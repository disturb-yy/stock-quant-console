# Frontend UI Guidelines

> 适用范围：本仓库所有新增或修改的 UI。  
> 本文定义 Agent 的执行规则与 UI 评审标准。视觉样式基础由 `design-system/DESIGN.md` 定义，具体 token、组件尺寸和页面差异由 `design-system/MASTER.md` 与页面文档定义。
>
> 核心目标：**让 Agent 能够自主完成日常 UI 工作，同时严格避免脱离设计系统、产生“AI 味”界面或在非必要场景反复请求确认。**

---

## 1. 视觉结论

本项目默认风格是**克制的数据研究终端**：

- 专业、可信、信息优先；
- 强调数据可读性、任务清晰度和可复核性；
- 默认采用设计系统定义的深色中性研究画布；
- 不追求营销海报式视觉，不采用泛 AI 产品常见的装饰性表达；
- 通过平面表面、细分隔线、留白、排版和少量语义色建立层级。

| 维度 | 默认决定 |
| --- | --- |
| 气质 | 冷静、清晰、可复核；数据和任务优先于装饰 |
| 画布 | 默认深色中性画布；仅在页面文档明确要求时使用浅色事务性表面 |
| 强调 | 一个主品牌强调色承担主 CTA、关键选中状态和少量关键数值 |
| 数据语义 | 涨跌、成功、错误、警告等使用各自语义色，不与品牌色混用 |
| 层级 | 依靠平面表面、1px 分隔线、留白和排版，不依靠光晕、厚阴影或漂浮效果 |
| 密度 | 允许紧凑，但分组、标签、数值和操作必须可快速扫读 |
| 动效 | 只解释状态变化或提供操作反馈，安静、短促，并支持减少动态 |

---

## 2. 规则优先级

UI 决策按以下顺序执行：

1. `design-system/DESIGN.md`：默认的视觉样式基础、层级、布局节奏与组件模式
2. 对应页面的 `design-system/pages/*.md`：页面目标、信息架构、状态、交互与已明确记录的偏离
3. `design-system/MASTER.md`：将视觉基础落为量策可用的 token、系统字体与组件尺寸
4. 本文：执行、审批与验收规则

适用规则如下：

- `DESIGN.md` 是日常 UI 工作的必读样式基础；其中的外部研究结论必须经 `MASTER.md` 的本地映射后实施，不能直接复制外部专有资产。
- 页面文档只有在明确标记“覆盖 DESIGN / MASTER”并说明原因时，才能偏离视觉基础或本地映射；普通页面补充不改变全局规则。
- 页面文档未涉及的内容继续继承 `DESIGN.md` 与 `MASTER.md`。
- 本文约束 Agent 的执行、审批和验收，不覆盖 `DESIGN.md`、页面文档或 `MASTER.md` 的具体视觉决定。
- `DESIGN.md` 与 `MASTER.md` 存在无法通过本地映射解决的冲突时，先更新并批准相应设计系统文档；不得在单个页面中临时择一执行。

### 2.1 页面文档不存在时如何处理

页面级文档不存在时，**不要因此停止任务或请求用户确认**。

默认行为：

1. 使用 `design-system/DESIGN.md` 的视觉样式基础；
2. 使用 `design-system/MASTER.md` 的本地 token 与实现映射；
3. 再使用本文的通用规则；
4. 若现有设计系统已经可以表达需求，直接完成实现；
5. 仅当任务需要改变视觉样式基础或本地映射时，才进入审批流程。

## 3. 指令强度

### 必须

未满足则不能视为 UI 交付完成。

### 推荐

默认优先采用，但不是阻塞条件。  
如果页面需求、可用性、已有组件或设计系统明确支持其他实现，Agent 可以自行选择并继续完成任务，无需额外请求确认。

### 禁止

默认不允许出现在正式 UI 中。  
若产品方向确实要求突破该限制，应先修改并批准对应设计系统或页面设计文档。

---

## 4. Agent 自主执行规则

### 4.1 默认继续，不因普通实现决策停顿

以下情况属于日常 UI 实现，Agent 应自主完成，不需要用户批准：

- 页面内部布局微调；
- 信息分组和排序；
- 组件组合方式；
- 表格列布局和横向滚动策略；
- 已有设计系统内的组件选择；
- 图表类型选择；
- 间距和对齐方式的实现；
- hover、selected、disabled、loading、empty、error、focus 状态；
- 响应式布局；
- CSS / Tailwind / CSS Module 等具体实现方式；
- 不改变视觉语义的重构；
- 修复已有页面的视觉缺陷。

当存在多个合理实现时，应基于：

1. 页面任务目标；
2. 数据可读性；
3. 已有设计系统；
4. 仓库现有实现；

自行选择最合理方案并完成任务。

不要因为“存在多个方案”就默认向用户请求确认。

---

## 5. 何时可以澄清

### 5.1 不应澄清的情况

以下情况应优先自行判断：

- 可从现有页面或设计系统推导；
- 可以采用成熟默认方案；
- 不影响产品语义；
- 不改变品牌方向；
- 可以在后续低成本调整；
- 只是视觉或工程实现细节。

### 5.2 可以澄清的情况

只有当缺失信息会实质改变产品含义，并且无法从仓库上下文推导时，才需要提问，例如：

- 页面核心业务目标互相矛盾；
- 同一数据字段存在两种业务含义；
- 用户明确要求在多个互斥产品方向中选择一个；
- 涉及不可逆或高成本的产品级改动。

如果任务可以安全地采用合理默认值完成，则应先完成，不要停在澄清阶段。

## 6. 审批要求

以下审批要求应保留。

### 6.1 必须获得明确批准

以下变更不能由 Agent 自行决定：

- 改变项目整体视觉方向；
- 新增或替换品牌主色体系；
- 修改全局字体体系；
- 修改全局字号层级；
- 修改全局圆角体系；
- 修改全局阴影体系；
- 修改全局间距 token；
- 引入新的全局组件库或视觉组件体系；
- 将默认深色研究终端改为另一套主要界面范式；
- 修改 `design-system/MASTER.md` 中的基础视觉原则；
- 为单个页面建立与全局设计系统不兼容的新视觉语言。

### 6.2 不需要审批

在已有设计系统内进行以下工作无需批准：

- 使用已有 token；
- 组合已有组件；
- 页面级信息架构调整；
- 页面内部响应式调整；
- 已有语义色的正确应用；
- 可访问性修复；
- 普通交互状态补全；
- 数据表、图表和面板布局优化。

---

## 7. Token 与组件约束

### 必须

- 使用已批准的语义 token；
- 优先复用现有组件和组件变体；
- 字体、字号、间距、颜色、圆角、阴影来自设计系统；
- 页面不得私建一套新的视觉语言。

### 禁止

不得为了“看起来更好”而直接硬编码新的：

- 品牌色；
- 语义色；
- 圆角；
- 阴影；
- 字号体系；
- 间距体系。

如果现有 token 无法表达需求：

1. 先判断是否可以通过现有 token 组合解决；
2. 若不能，并且确实需要新增全局 token，则提出设计系统修改建议；
3. 未批准前不要私自在页面中创建替代体系。

---

## 8. 页面与表面

### 必须

- 页面首先应是一个可工作的研究界面；
- 任务、数据、筛选和下一步行动应清晰可见；
- 主要层级通过表面、分隔线、排版和留白建立。

### 推荐

- 使用深浅有序的平面表面；
- 使用 1px 细分隔线区分区域；
- 留白用于信息分组和阅读节奏，而不是制造空洞的“高级感”；
- 强调一个区域时，优先只提升一个视觉维度：颜色、字重、大小、边框或位置。

---

## 9. 排版与数据

### 必须

- 遵循设计系统定义的中文字体、字号和行高；
- 数据不能只通过颜色表达含义；
- 重要状态应同时具有文字、符号、数值或结构提示。

### 推荐

- 价格、比例、日期、统计值使用等宽数字或 `tabular-nums`；
- 数值列保持一致对齐；
- 使用标签、表头、分组标题和低对比网格线提高可扫读性；
- 文案应简洁、可核验，优先表达状态、来源、限制或下一步。

---

## 10. 组件与交互

### 必须

- 主按钮、次按钮、文本操作具有明确优先级；
- 一个视图通常只突出一个主行动；
- 保留可见焦点；
- 可点击目标和 label 清晰；
- selected、hover、disabled、loading、empty、error 状态可直接辨认；
- 窄屏不能通过缩小关键文字来强行塞入所有内容。

### 推荐

- 卡片只用于信息分组或交互容器；
- 同类卡片保持一致的标题、内容、元数据和操作顺序；
- 图表必须以数据阅读为目标，不作为装饰背景。

---

## 11. 图表

图表是研究工具，不是视觉海报。

### 必须

- 主轨迹、坐标、标签、图例和关键数值具有清晰层级；
- 数据含义不能只依赖颜色；
- 关键数值尽量邻近图表或对应轨迹展示；
- 涨跌等金融数据遵循设计系统定义的语义色。

### 禁止

- 无意义渐变面积；
- 装饰性阴影；
- 过粗轨迹；
- 缺少可读标签；
- 自动闪烁报价；
- 为增强“科技感”加入不承载数据含义的视觉效果。

---

## 12. 动效与响应式

### 必须

- 支持 `prefers-reduced-motion`；
- 关闭动效后信息与操作仍完整；
- 移动端优先保证阅读和操作。

### 推荐

- 动效仅用于按钮反馈、选项卡、展开收起和状态切换；
- 密集区域在移动端优先改为纵向分组；
- 表格必要时横向滚动，不压缩关键列和文字。

---

## 13. 禁止的“AI 味”与营销视觉

以下视觉在正式研究界面中默认禁止：

- 未经页面文档明确批准的紫蓝、彩虹、霓虹或 mesh 渐变大面积背景；
- 发光边框、模糊光晕；
- 粒子、星空、流体球；
- 无业务意义的悬浮 3D 物体；
- 玻璃拟态、半透明叠卡、难以辨认边界的磨砂层；
- 超出页面文档或 MASTER 所定义层级的超大 Hero 标题；
- 巨型圆角；
- 大量 pill 标签；
- 漂浮卡片瀑布流；
- 为“智能感”加入的无数据意义动画；
- “AI 驱动”“一键洞察”“颠覆”“稳赚”等缺少证据的营销话术。

### 例外

如果页面本身就是营销、品牌或活动页面，应以对应页面设计文档为准。  
不得为了临时需求绕过全局设计系统。

---

## 14. 数据语义保护

### 禁止

- 主品牌色大面积铺满背景或所有按钮；
- 上涨、下跌、成功、错误、警告共用同一颜色语义；
- 红绿大色块制造情绪化紧迫感；
- 闪烁报价；
- 以缩小字体、压缩行高、去掉标签来追求信息密度；
- 将 hover 色差作为唯一交互提示。

---

## 15. 外部参考使用规则

### 允许

外部产品可以用于：

- 研究布局；
- 分析信息架构；
- 研究数据组织方式；
- 研究交互模式。

### 禁止

不得直接复制：

- 商标；
- 品牌字体；
- 品牌色；
- 文案；
- 截图；
- 专有图标；
- 品牌资产；
- 对方特有视觉语言。

`DESIGN.md` 是已被项目采用的视觉样式基础；它对外部研究的表达必须经本项目的 token、可访问性和专有资产边界转换后使用，不能把来源产品本身当作可复制的设计系统。

---

## 16. UI 任务完成标准

Agent 不应在“分析完成”后就结束 UI 任务。

当用户要求实现 UI 时，完成至少包括：

1. 阅读适用的页面设计文档；
2. 检查 `design-system/MASTER.md`；
3. 完成实际页面或组件实现；
4. 补齐必要的交互状态；
5. 检查桌面与窄屏；
6. 检查键盘焦点和可访问性；
7. 检查 `prefers-reduced-motion`；
8. 检查是否引入未经批准的新 token；
9. 检查是否出现禁止的 AI / 营销视觉；
10. 汇报实际存在的偏离项或限制。

### 不完整交付

以下不应视为任务完成：

- 只输出设计分析而未实现用户要求的页面；
- 只给建议并等待用户继续确认；
- 找不到页面文档后直接停止；
- 因存在多个合理实现方案而暂停；
- 仅完成桌面端但忽略明显需要的响应式状态；
- 以“可以继续帮你实现”为结尾，但实际任务本身尚未完成。

---

## 17. UI 交付自检

- [ ] 页面符合“克制的数据研究终端”方向；
- [ ] 数据和任务优先于装饰；
- [ ] token 来自页面文档或设计系统；
- [ ] 没有私建品牌色、圆角、阴影、字号或间距体系；
- [ ] 一个视图只有清晰的主行动；
- [ ] 主品牌色没有被滥用；
- [ ] 表面层级由平面色、细线、留白和排版建立；
- [ ] 没有无依据的渐变、光晕、玻璃拟态或装饰性 3D；
- [ ] 中文文案、数字、表格和图表可快速扫读；
- [ ] hover、selected、disabled、loading、empty、error、focus 状态清晰；
- [ ] 桌面与窄屏均可用；
- [ ] 支持减少动态；
- [ ] 没有复制外部品牌资产；
- [ ] 用户要求的实际 UI 工作已完成，而不是只停留在分析阶段。

---

## 18. 变更本指南

当产品方向确实改变时：

1. 优先修改并批准 `design-system/DESIGN.md` 的视觉基础或 `design-system/MASTER.md` 的本地映射；
2. 再同步对应页面设计决策与本文；
3. 不要通过单个页面的临时偏离改变默认风格。
